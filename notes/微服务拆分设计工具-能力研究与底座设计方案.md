# 微服务拆分设计工具 —— 能力研究与底座设计方案

> 本文是比赛底座的设计蓝本。结论：**以 BAC4 为前端骨架 fork 开发，融合 DDD Toolbox 的分析工具与普元 EOS DDD 的微服务元素，补齐"微服务专属"元素集，新增 Python(FastAPI) 后端与 AI 评审服务；以画布设计为主、模型可导出为结构化文本/DSL 供 AI 评审，内置标准化元数据/标签。**
>
> **已定决策（2026-07-31）**：① 下一步先评审本方案再开工；② 后端用 **FastAPI**；③ **不做 DSL 文本双模编辑**，但模型必须能**导出结构化文本/DSL**（供 AI 评审与外部工具消费）。

---

## 1. 目标与定位

- **聚焦"微服务拆分设计"**，不做大而全的通用建模工具（华为 CodeArts Model 那种太重、偏 4+1 全视图建模，是反面参照）。
- **避免复杂 UML 建模**，难易适中；但"微服务如何设计所需的元素"要尽量充分。
- **以画布设计为主**；模型可**导出为结构化文本/DSL**（供 AI 评审与外部工具消费）。暂不做 DSL 文本反向编辑与双向同步（已定决策，降复杂度）。
- **前后端完整程序**：前端画布/DSL，后端 **Python**。
- **内置标准化元数据/标签**（受控词汇 + 结构化字段），让后续 **AI 智能评审**可稳定判断。
- **底座融合三源之长**：
  - BAC4 → C4 模型（系统/容器/组件）+ 关系 + 多格式导入导出。
  - DDD Toolbox → 用户故事、事件风暴、限界上下文画布等分析工具。
  - 普元 EOS DDD / 微服务模式 → 领域事件、命令、CQRS、API 网关、消息中间件等微服务专属元素。

---

## 2. 深入研究结论：微服务拆分设计工具需要哪些能力

一个"够用又不臃肿"的微服务拆分设计工具，能力可分为 **4 个建模层 + 2 个支撑层**：

### 2.1 领域分析层（发现边界）— 来自事件风暴 / 领域故事 / 用户故事
用业务叙事驱动边界识别，是"拆分"的输入。
- 元素：用户故事(User Story)、领域事件(Domain Event)、命令(Command)、参与者/角色(Actor)、只读模型/视图(Read Model)、热点/待决(Hotspot)、外部系统。
- 能力：从用户故事/事件流里聚类出候选聚合与边界（学术参照 **SEMGROMI**：用用户故事语义相似度聚类识别微服务）。

### 2.2 战略设计层（划边界）— 来自 DDD 战略设计 / Context Mapper
- 元素：域(Domain)、子域(Subdomain：核心/支撑/通用)、限界上下文(Bounded Context)。
- **上下文映射关系(Context Mapping)**：Partnership、Shared Kernel、Customer/Supplier、Conformist、Anti-Corruption Layer(ACL)、Open Host Service(OHS)、Published Language、Separate Ways。
- 能力：拆分/合并上下文与聚合，迭代优化耦合与内聚（架构重构 Architectural Refactoring）。

### 2.3 战术设计层（定服务内部结构）— 来自 DDD 战术设计 / 普元 EOS DDD
- 元素：聚合(Aggregate，含聚合根)、实体(Entity)、值对象(Value Object)、领域服务(Domain Service)、领域事件(Domain Event)、命令(Command)/查询(Query，CQRS)、仓储(Repository)、策略(Policy)、工厂(Factory)。
- 能力：一个聚合 ≈ 一个一致性边界，是微服务粒度的重要依据。

### 2.4 微服务/物理架构层（落地为服务与通信）— 来自 BAC4 C4 + 微服务模式 + EOS
这是"拆分结果"的呈现层，也是要在 BAC4 基础上**重点补强**的部分。
- 服务节点：微服务(Microservice ≈ C4 Container)、组件(Component)、外部系统、人/Actor。
- **基础设施/通信节点（新增，参考 EOS/微服务模式）**：API 网关(API Gateway)、BFF、消息中间件(Message Broker / MQ)、数据库/数据存储、**文件/对象存储(File / Object Storage)**、缓存、注册中心/配置中心、Saga 编排器。
- 关系类型：同步调用(REST/gRPC)、异步消息(发布/订阅、事件/命令经中间件)、数据依赖、编排/协同(Saga)。

### 2.5 支撑层 A：评估度量（AI 评审的量化基础）
- 指标：耦合(越低越好)、内聚(越高越好)、通信 chattiness、跨服务一致性(强/最终)、边界合理性。
- 参照：**Service Cutter 16 项耦合准则**、**华为 CodeArts 的 30+ 架构检查规则集**。

### 2.6 支撑层 B：模型交换 / 生成（沿用并扩展 BAC4）
- 导入导出：BAC4 JSON、Structurizr JSON、PlantUML、Mermaid、Draw.io、Markdown。
- 可扩展：OpenAPI / AsyncAPI 服务契约、微服务代码骨架（作为选手增强项）。

## 4. 标准化元数据 / 标签 Schema（为 AI 智能评审服务）

**核心思想**：AI 评审要稳定，就不能只喂自由文本；必须有**受控词汇(controlled vocabulary) + 结构化字段**。

### 4.1 通用元数据（所有节点）
```
id, name, description, layer(analysis|strategic|tactical|microservice),
type, subdomainType(core|supporting|generic), owner/team,
technology, tags[]（受控标签）
```

### 4.2 微服务节点专属
```
stateful(bool), ownsData[]（数据所有权，判共享库反模式）,
exposesApi[]（对外API/契约引用）, dependsOn[]（依赖服务）,
sla, deploymentUnit, scalability
```

### 4.3 关系专属
```
kind(sync|async|data|orchestration),
protocol(REST|gRPC|MQ|…), consistency(strong|eventual),
couplingType(context-mapping 模式), frequency, contractRef
```

### 4.4 受控标签词表（示例，可扩展）
- 子域：`core` / `supporting` / `generic`
- 通信：`sync` / `async` / `pub-sub`
- 一致性：`strong` / `eventual`
- DDD：`aggregate-root` / `anti-corruption-layer` / `open-host-service` / `published-language`
- 风险信号：`shared-database` / `chatty` / `god-service` / `anemic-model`

> 这套 schema 就是底座交给 AI 的"结构化输入"，也是选手做智能评审的抓手。

## 5. AI 智能评审维度（选手增强核心，底座**只预留不实现**）

> **已定决策**：MVP 阶段**不实现任何 AI 评审逻辑**。底座只做三件事：
> ① 把第 4 节的**标准化元数据/标签 schema 落地**（元素/关系上可填、可校验）；
> ② 保证模型能**导出结构化 JSON/DSL**（AI 的输入就绪）；
> ③ **预留一个 AI 评审接口占位**（定义好输入/输出契约，返回"未实现"）。
> 具体评审逻辑留给选手实现。下面的维度是**给选手的参考规格**，不是底座要交付的功能。

参考华为 CodeArts "30+ 规则集"与 Service Cutter 耦合准则，评审至少覆盖：

1. **边界合理性**：聚合过大/过小；边界是否横跨强一致性事务。
2. **耦合/内聚**：同步调用链过长、循环依赖、chatty 通信、上帝服务。
3. **DDD 反模式**：贫血模型、共享数据库、大泥球、缺 ACL。
4. **一致性/事务**：跨服务误用强一致；缺 Saga/最终一致。
5. **命名/统一语言一致性**：术语与限界上下文是否一致。
6. **通信/中间件合理性**：网关滥用、本应异步却同步、消息中间件缺失。

**输出**：问题清单 + 严重度 + 定位(元素/关系) + 改进建议 + 重构方案。
**实现建议**：静态规则(快速确定) + LLM(语义与建议) **双通道**；输入 = 第 4 节的规范化模型 JSON。

## 6. 架构方案

```
┌────────────────────────── 前端 (fork BAC4) ──────────────────────────┐
│              画布 (React 19 + React Flow + Zustand)                   │
│        ↑ 扩展元素类型 / 属性面板 / 受控标签 / 元数据字段              │
│                      规范化模型 (JSON，单一事实源)                     │
│                      → 导出：JSON / DSL 文本 / Structurizr / PlantUML │
└───────────────────────────────┬──────────────────────────────────────┘
                                 │ REST / JSON
┌───────────────────────────────▼──────────────────────────────────────┐
│                    后端 (Python, FastAPI)                             │
│  · 项目 CRUD + 模型保存/加载(SQLite)   · 模型 schema 校验(受控词表)   │
│  · 导出转换(JSON / DSL 文本 / Structurizr / PlantUML)                │
│  · 受控标签/元数据词表接口(供前端属性面板)                            │
│  · AI 评审接口：**仅占位，定义契约、返回未实现**(选手实现)           │
└───────────────────────────────────────────────────────────────────────┘
```

- **画布为主，无 DSL 反向编辑**：用户只在画布上建模；DSL/结构化文本是**只读导出产物**，主要喂给 AI 评审，也可给外部工具（Structurizr/PlantUML）。
- **导出格式**：规范化 JSON（AI 评审主输入）+ 一种人类可读 DSL 文本（语义对齐 DDD + 微服务，可基于 Structurizr DSL 扩展）+ 沿用 BAC4 的 PlantUML/Mermaid/Draw.io。
- **后端 Python**：FastAPI（轻、异步、自带 OpenAPI 文档、易接 LLM）；LLM 用 Claude（`claude-opus-4-8` / `claude-sonnet-4-6`）——LLM 相关仅为选手预留，底座不实现。

### 6.1 后端功能 / 数据库 / 画布保存（明确回答）

**后端 MVP 主要提供的功能（AI 评审只占位不实现）：**

| 功能 | 说明 | 接口示例 |
|------|------|----------|
| 项目管理 | 设计项目的增删改查，一个项目 = 一份模型 | `GET/POST/PUT/DELETE /api/projects` |
| 模型保存/加载 | 保存/读取规范化模型 JSON（元素+关系+元数据+标签+画布布局） | `PUT /api/projects/{id}/model` · `GET /api/projects/{id}/model` |
| 模型校验 | 按受控词表/schema 校验模型合法性（AI 评审前置，纯结构校验，不含语义） | `POST /api/projects/{id}/validate` |
| 导出 | 导出 JSON / DSL 文本 / Structurizr / PlantUML | `GET /api/projects/{id}/export?format=dsl` |
| 词表接口 | 返回受控标签/元数据字段定义，供前端属性面板下拉 | `GET /api/vocab` |
| 版本快照（可选） | 保存模型历史版本，便于回溯/对比 | `GET/POST /api/projects/{id}/versions` |
| AI 评审（**占位**） | 定义好输入=模型JSON、输出=评审报告契约，**返回 501 未实现** | `POST /api/projects/{id}/review` |

**数据库：MVP 用 SQLite（零配置、单文件、够比赛底座）**，经 SQLAlchemy 访问，未来可平滑换 PostgreSQL。
表结构极简（模型本身是文档，不拆成一堆关系表）：
```
projects(id, name, description, created_at, updated_at, model_json TEXT)
model_versions(id, project_id, model_json TEXT, created_at)   -- 可选，做快照
```
即：**整份规范化模型以 JSON 文本存一列**（document 风格），避免把聚合/服务/关系拆成大量表带来的复杂度。

**画布怎么保存：**
1. 画布状态（React Flow 的节点/连线 + 每个元素的属性/标签/元数据 + **position 坐标**）在前端序列化成**一份规范化模型 JSON**——这就是"单一事实源"。
2. **两级保存**：
   - **前端 localStorage 自动保存**（沿用 BAC4，每 30s + 关闭页面时，离线兜底）；
   - **"保存到项目"** → 把 JSON `PUT` 到后端 → 存进 SQLite 的 `projects.model_json`。
3. **加载**：打开项目 → 后端 `GET model_json` → 前端反序列化还原画布（含布局坐标，布局不丢）。
4. 导出的 DSL/JSON 只是这份模型的**只读投影**，供 AI 评审与外部工具消费。

## 7. 底座 vs 选手增强（比赛设计）

| | 内容 |
|--|--|
| **底座交付** | 画布+DSL 双模建模；完整微服务元素集(分析/战略/战术/微服务四层)；标准化元数据/标签；导入导出；AI 评审的接口 + 最小可跑样例 |
| **选手增强** | ① 更强的 AI 评审规则/维度；② 自动拆分建议(输入用户故事/实体→建议服务边界)；③ 评审结果可视化；④ 生成 OpenAPI/AsyncAPI 契约或代码骨架 |
| **评分点** | 元素/关系表达完整性、AI 评审准确度与可解释性、拆分合理性、工程质量、创新性 |

## 8. 建议的 MVP 范围（难易适中）

1. fork BAC4，跑通前端；抽出规范化模型。
2. 扩展元素：加 API 网关、消息中间件、Saga、Database，及子域/聚合层最少集。
3. 加受控标签与关键元数据字段(第 4 节子集)。
4. 加 Python FastAPI 后端：项目 CRUD、模型保存/加载(SQLite)、schema 校验、导出、词表接口；**AI 评审接口仅占位不实现**。
5. 导出：规范化 JSON + 一种 DSL 文本（供 AI 评审）；**不做 DSL 反向编辑**。
